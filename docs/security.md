# Security notes

These are review notes written while documenting the code. They are **not** an audit. The
contract has not been deployed or externally reviewed.

## Trust model

- **Deployer.** The deployer picks `token`, `merkleRoot`, `expiry` and `sweepTo` once, and has no
  powers after deployment. There is no owner, no pause switch and no way to withdraw early.
- **Whoever builds the tree** decides who gets what. The contract cannot tell whether the tree is
  correct or matches the funding.
- **`sweepTo`** gets every unclaimed token after expiry. It has no special rights before then, and
  it cannot sweep early.
- **Callers.** Anyone can call `claim` or `sweep`. Neither call pays the caller anything.
- **Token.** The token contract is trusted to report balances and move tokens honestly. A
  malicious token can do anything with its own balances. The contract only guarantees its own
  bookkeeping: each index is paid at most once.

## Properties the tests check

The suite has 63 tests, run with `forge test`, including fuzz tests.

- The leaf encoding and sorted-pair hashing match a tree generated by the real
  `StandardMerkleTree`. The tests use a hard-coded vector, which
  [merkle-tree.md](merkle-tree.md) reproduces.
- Each index is paid at most once. The same holds for zero-amount leaves, repeat callers and a
  token that re-enters `claim`.
- Claims work at `t <= expiry` and sweeps work at `t > expiry`. For any time, exactly one of the
  two is open.
- Tokens go only to `account` (claims) or `sweepTo` (sweeps), never to `msg.sender`.
- If a transfer fails, the claimed bit is rolled back, so the claim can be retried.
- Tokens that return no data (USDT style) are accepted. Tokens that return `false` or have no code
  are rejected. Return data shorter than 32 bytes causes a revert.
- Single-hashed-leaf trees and internal-node "leaves" are rejected.
- The bitmap has no cross-talk at word boundaries (255/256) or at `type(uint256).max`.

One test comment overstates coverage. In `test_claim_revertsWhenTokenReturnsMalformedData`, the
comment mentions 64-byte return data, but only the 32-byte case is actually exercised.

## Known limitations and hazards

These are behaviours of the current code, not bugs relative to the brief. Each one matters for
real funds.

1. **No solvency check.** Nothing ties the tree total to the balance. If the contract is
   underfunded, claims are paid first come, first served until the balance runs out, and
   later claims revert with `TokenTransferFailed()` until someone tops up.
2. **Fee-on-transfer and rebasing tokens.** The contract sends exactly `amount`. If the contract
   received less than the tree total, or the balance shrinks, it runs out early (see 1). A
   recipient of a fee-on-transfer token also receives less than `amount`.
3. **Blocklists.** If `sweepTo` is blocklisted by the token, every `sweep()` reverts and the
   leftover tokens are stuck forever, since `sweepTo` is immutable. A blocklisted `account`
   cannot claim, and its allocation goes to `sweepTo` after expiry.
4. **Tokens that revert on zero-value transfers.** Zero-amount leaves can never be claimed
   (`TokenTransferFailed()`, and the bit is rolled back). `sweep()` on an empty contract
   reverts instead of emitting `Swept(0)`. This was checked with a throwaway test and is not in
   the committed suite.
5. **Codeless or wrong `token`.** The constructor accepts any nonzero address. With a codeless
   token, `claim` reverts with `TokenTransferFailed()` and `sweep` reverts with no error data.
   Deploying to an address where a token only exists on another chain gives you a useless
   contract.
6. **Stranded assets.** ETH cannot be sent to the contract (it has no `receive` or `fallback`),
   except by force, for example with `selfdestruct`. ERC-20s other than `token` sent to the
   contract can never be recovered. Mistaken deposits of `token` can only leave through claims
   before expiry, or through `sweep()` after.
7. **`account == address(0)`** is not rejected. A leaf for the zero address pays the zero address
   if the token allows it.
8. **Duplicate indices** in the tree mean only the first of those rows to be claimed gets paid.
9. **Timestamp dependence.** The window is based on `block.timestamp`. Validators can shift the
   timestamp slightly, so a claim sent in the last seconds before `expiry` may land on either
   side of it.
10. **Front-running claims** is harmless. Whoever submits, the funds go to `account`. A claimant
    whose transaction is front-run just sees `AlreadyClaimed()`.

## Before using this with real funds

- Get an independent review or audit.
- Pin a compiler version. The pragma is floating (`^0.8.20`) and there is no `foundry.toml`.
- Write and review a deploy script that checks the deployed immutables.
- Check that the token has none of the behaviours in items 2 to 4.
- After funding, confirm `token.balanceOf(distributor)` is at least the tree total.
